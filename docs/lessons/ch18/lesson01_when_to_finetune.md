# 第十八章第1节：什么时候需要微调：场景与决策

大家好，我是秋天。

前面十七章，你的 Agent 基本都靠"prompt + RAG + 工具"干活，模型本身没动过——用的就是 DashScope / OpenAI 的现成大模型。这其实是对的：**绝大多数场景，你根本不需要微调**。但总有那么一些场景，prompt 写到吐、RAG 调到崩，效果还是差一口气。这时候，"微调（Fine-tuning）"就该进你的工具箱了。

这一节我们不写代码（代码在 lesson02），先把**决策**讲透：到底什么时候该微调、什么时候别碰。很多同学一上来就"微调万能论"，烧了几万块 GPU 钱，效果还不如改两行 prompt——这是最典型的"用战术勤奋掩盖战略懒惰"。

这节课讲什么、学完掌握什么：

- 讲什么：① 微调 vs RAG vs Prompt 的三元决策框架；② 三个明确该微调的信号（RAG 不够、领域强约束、风格/格式固化）；③ 三个**不该**微调的陷阱；④ 一张可直接用的决策表。
- 学完掌握：你能对着一个业务需求，说出"该微调 / 该 RAG / 该改 prompt"；你知道微调的真实成本（数据、算力、维护）在哪；你能避免"为微调而微调"的浪费。

<callout emoji="💡"><p>招聘映射：微调在 JD 里是明确的"加分项"（spec 第三章"加分项：模型微调 LoRA/QLoRA、推理优化"）。面试官不会指望你天天微调，但他要确认你"知道什么时候该用、什么时候不该用"——这个判断力的含金量，远高于"我会跑一个微调脚本"。这一节练的就是这个判断力。</p></callout>

## 一、先摆正：微调不是银弹，是最后手段

我给一个优先级铁律，记住它：

```
解决问题优先级（从便宜到贵、从易到难）：
  1. 改 Prompt / 上下文工程（第十五章）        ← 先试这个，几乎零成本
  2. RAG / 检索增强（第七章）                  ← 知识类问题首选
  3. 工具 / 工作流编排（第四、九章）           ← 能力类问题靠工具补足
  4. 微调 Fine-tuning（第十八章）             ← 上面都不行才考虑
  5. 预训练 / 从头训                           ← 除非你是大厂基础模型团队，否则别想
```

为什么微调垫底？因为它**贵、慢、难维护、易过拟合**：

```text
微调的真实成本（很多人只算了 GPU）：
- 数据成本：几百~几万条高质量标注，人工标注很贵
- 算力成本：一次训练几小时~几天 GPU，反复调参
- 维护成本：基础模型一升级，你可能要重训；数据漂移要持续更新
- 风险成本：微调可能"灾难性遗忘"——学会新任务，忘了旧能力
```

<callout emoji="⚠️"><p>反模式："老板说要搞微调，我就去搞"。没有决策依据的微调，90% 是在用 GPU 烧钱掩盖"prompt 没写好、RAG 没调通"的事实。先问自己：前三个手段我真试透了吗？</p></callout>

## 二、决策框架：三元对比

把三个手段放到一张表，看清各自擅长什么：

```text
手段        擅长解决的问题              不擅长
─────────────────────────────────────────────────────────────
Prompt      任务说明、格式指令、角色设定   海量私域知识、稳定风格固化
RAG         私域知识问答、最新信息检索     稳定输出风格、强领域推理约束
微调        稳定风格/格式、强领域模式、    实时知识更新（要重训才更新）
           低延迟低成本重复任务、        小样本泛化（数据少易过拟合）
           特定"口吻/结构"固化
```

一句话口诀：**知识用 RAG，能力用工具，风格/强约束用微调，说明用 Prompt**。这四句能解决你可能遇到的 90% 选型困惑。

## 三、信号一：RAG 不够时（知识有了 but 不会"用"）

RAG 能解决"知识在哪"，但解决不了"怎么用知识"这类**深领域推理/模式**。典型场景：

```
场景：医疗理赔 Agent
- RAG 能检索到"条款 A 第 3 条说……"（知识有了）
- 但模型不会"按这家保险公司的特定逻辑链"去套用条款做判定
  → 这是"领域强推理模式"，RAG 给知识，微调教"怎么推理"
```

判断信号：
- 你已经把 RAG 检索质量、重排序、查询改写都调过了，召回没问题；
- 但模型对"检索到的内容"组织、推理、套用方式总不对；
- 这种"不对"是**稳定、可归类的模式**（不是随机抽风）。

此时微调（用领域推理样本）能让模型学会"你们家特有的推理套路"。

<callout emoji="✅"><p>关键区分：RAG 解决"知不知道"，微调解决"会不会按我们的方式做"。如果你的问题是"模型不知道我们公司内部规定"，先 RAG；如果是"模型知道规定但总用错方式套用"，考虑微调。两者常常组合：RAG 供给知识 + 微调固化推理方式。</p></callout>

---

## 四、信号二：领域强约束（规则/合规硬边界）

某些领域有**不可违背的强约束**，靠 prompt 软约束不够稳——prompt 说"千万别泄露患者隐私"，但长对话里模型偶尔还是会嘴快。微调能把这种约束"焊死"进模型行为。

```text
强约束场景举例：
- 金融：回答必须包含"投资有风险"免责声明，且不能给具体买卖建议
- 医疗：不能给确诊结论，只能给就医建议
- 法律：必须标注"不构成法律意见"
- 客服：特定品类必须用指定话术，偏差即违规
```

这类"每次都必须、偏差即事故"的约束，微调比 prompt 更稳，因为约束成了模型行为的一部分，而非每次靠指令"提醒"。

<callout emoji="💡"><p>但注意：强约束 ≠ 全部靠微调。安全红线（不泄露 PII、不越权调工具）更应该用 lesson03 的**沙箱 + 输出护栏 + 脱敏**在系统层兜底，而不是指望模型"自觉"。微调负责"大概率不错"，系统兜底负责"绝不出格"——两层都要。</p></callout>

---

## 五、信号三：风格 / 格式固化（高重复、低成本优先）

这是**最划算**的微调场景：把"稳定输出风格/格式"固化进模型，换来低延迟、低成本、高一致。

```
高价值风格/格式固化场景：
- 客服：固定语气 + 固定工单结构（每次省大量 prompt token）
- 代码：固定代码风格/注释规范生成
- 报告：固定报告模板（摘要-分析-建议三段式）
- 抽取：稳定结构化抽取（NER / 字段提取，格式零容错）
```

为什么划算？因为"风格/格式"不需要海量知识，几百~几千条高质量样本就能见效；且固化后**推理时不用再塞长 prompt**，延迟和成本都降。

```text
对比：每次靠 prompt 约束格式
   system: "请用 JSON 返回，字段为{name,age,risk}，风格专业简洁……"（每次 ~200 token）
vs 微调后：
   直接给输入，模型稳定输出规定 JSON（prompt 只需 ~20 token）
→ 单次成本降，高并发下累计省很多
```

<callout emoji="✅"><p>风格/格式固化是"投入产出比最高"的微调场景，也是 Java 工程师最容易落地的——你不需要懂多少深度学习，只要准备好"输入-输出"配对样本，用 PEFT（lesson02）跑一个 LoRA 就行。很多企业的"内部报告生成""工单结构化"都是这个套路。</p></callout>

## 六、三个不该微调的陷阱

讲了该微调的，必须讲**不该**微调的，避免你踩坑：

### 陷阱 1：用微调当数据库（知识存模型里）

```text
❌ 错误：把公司 10 万条产品手册微调进模型，以为模型"记住了"
✅ 正确：知识用 RAG，模型只负责"检索后组织回答"
原因：模型记知识又慢又贵又易过时；RAG 实时、可更新、可溯源
```

### 陷阱 2：数据不够硬上（小样本过拟合）

```text
❌ 错误：50 条样本就微调，结果模型只会这 50 条的样子，泛化崩了
✅ 正确：风格/格式类几百条起；领域推理类最好上千条且覆盖边界
原因：数据少 → 过拟合 → 灾难性遗忘，不如不微
```

### 陷阱 3：忽视基础模型升级（维护债）

```text
❌ 错误：在 qwen-1.5 上微调完，qwen-2.5 出了，发现旧模型能力全面落后
✅ 正确：微调产物绑定基础模型版本，升级要重训并重新评测
原因：基础模型迭代快，微调是"债"，要纳入版本管理
```

<callout emoji="⚠️"><p>最贵的微调是"白调"。白调的典型表现：效果提升 < 改 prompt 的提升、维护成本 > 收益、模型一升级全废。动手前先用第十六章的评测集（RAGAS / EvalScope）量化"微调 vs 不微调"的差异，没差异就别调。</p></callout>

## 七、决策表：对着需求打勾

把前面浓缩成一张可直接用的决策表：

```text
你的需求                                      首选手段
────────────────────────────────────────────────────────────
"模型不知道我们内部规定/最新资料"            RAG（第七章）
"模型知道 but 老用错方式套用"                微调（领域推理）
"每次必须含免责声明/固定话术，偏差即违规"     微调 + 系统护栏(lesson03)
"稳定输出固定格式/风格，高并发省成本"         微调（最划算）
"任务说明/角色设定"                          Prompt（第十五章）
"需要调外部系统/计算"                        工具/工作流（第四、九章）
"实时性强的知识"                            RAG（别微调，会过时）
"样本 < 几百条"                             先别微调，用 Prompt+RAG
```

<callout emoji="💡"><p>我的经验法则：先花 80% 精力把 Prompt + RAG + 工具做到位，剩下 20% 的真正硬骨头（稳定风格/强约束/领域推理）才交给微调。绝大多数团队卡在"前 80%"没做透，就急着上微调，结果两头不讨好。</p></callout>

## 七（续）、微调数据长什么样：从哪来、怎么造

决定微调成败的，往往不是方法，是**数据**。很多同学以为"我有方法就行"，结果发现连训练样本格式都没见过。这里给你一个真实可用的样本形态（指令微调的 JSONL）：

```jsonl
{"messages": [
  {"role": "system", "content": "你是某银行投顾助手，回答须含免责声明，不给具体买卖建议。"},
  {"role": "user", "content": "我风险偏好保守，有10万闲钱怎么配置？"},
  {"role": "assistant", "content": "建议以货币基金与国债为主，占比约70%……（投资有风险，本回答不构成具体买卖建议）"}
]}
{"messages": [
  {"role": "system", "content": "你是工单结构化抽取器，输出固定JSON字段{order_id,reason,level}。"},
  {"role": "user", "content": "订单A123因物流延迟用户投诉，紧急"},
  {"role": "assistant", "content": "{\"order_id\":\"A123\",\"reason\":\"物流延迟\",\"level\":\"紧急\"}"}
]}
```

数据从哪来？四条现实路径：

```text
数据来源（从便宜到贵）：
1. 历史日志挖掘：把过去客服对话/工单里"用户问-人工答"配对抽出来（最常见）
2. 模型蒸馏：用强模型（GPT-4/qwen-max）对一批输入生成"理想输出"作样本
3. 人工标注：质量最高但最贵，用于边界/难例
4. 合成数据：按模板批量生成（风格/格式类最有效）
```

<callout emoji="✅"><p>数据质量 > 数据数量。1000 条干净、覆盖边界的样本，远胜 10000 条噪声样本。尤其要包含"难例"和"边界 case"——模型最常在边界翻车。这也是为什么微调前要先用评测集（第十六章）找出模型的薄弱点，针对性造数据。</p></callout>

## 七（再续）、成本量化：到底烧多少钱

决策不能拍脑袋，得算账。一张典型的 LoRA 微调成本估算（以 7B 模型为例）：

```text
项目                  量级（参考，随行情变动）
─────────────────────────────────────────────────
数据准备              人工标注 ~¥50-200/条（专业领域更贵）
                       3000 条专业标注 ≈ ¥15万-60万
GPU 算力（LoRA）       单卡 A100 72G，几小时~1天
                       约 ¥200-800/次训练（云按需）
多次调参/重训         通常 5-10 次才收敛 ≈ ¥1000-8000
基础模型升级重训       每次升级都要重来（维护债）
─────────────────────────────────────────────────
合计首轮              ≈ ¥15万-60万 + 算力（知识类更贵）
```

对比 RAG 的成本：

```text
RAG 成本：向量库 + Embedding 调用 + 检索，几乎无训练
         → 首轮可能 ¥0 训练费，日常仅 API 调用费
微调成本：数据 + 算力 + 维护，且模型升级要重训
```

这就是为什么"知识类先 RAG"——不仅效果好，还便宜得多。

<callout emoji="⚠️"><p>算账时别忘了"机会成本"：一个算法工程师 2 周做微调，如果换成把 Prompt+RAG 调透，可能效果更好、还快。微调的 ROI 必须在"前三个手段试透后"才评估。别让"想用新技术"压倒"性价比"。</p></callout>

## 七（补）、和评测闭环（第十六章）怎么配合

微调不是"训完就上"，必须过评测关。把第十六章的评测金字塔用在这里：

```text
微调前：用 RAGAS / EvalScope 跑基线（不微调的得分）
微调后：同一评测集再跑，对比
   ┌─────────────────────────────────────────┐
   │ 指标        基线    微调后   结论          │
   │ 格式合规率  0.71    0.98    ✅ 显著提升    │
   │ 领域准确率  0.68    0.79    ✅ 提升        │
   │ 通用能力    0.85    0.83    ⚠️ 轻微遗忘   │
   │ 成本/次     ¥0.012  ¥0.008  ✅ 下降       │
   └─────────────────────────────────────────┘
   决策：格式/领域提升明显、通用仅轻微降、成本降 → 可上线
        但若通用能力掉太多 → 调整 LoRA 超参或数据配比，防遗忘
```

<callout emoji="💡"><p>"灾难性遗忘"是微调的隐形杀手：模型学会新任务，旧能力掉了。评测必须同时测"新任务"和"通用能力"两条线。如果通用掉太多，说明数据配比失衡或学习率太大——这时候未必是"不该微调"，而是"没微好"。</p></callout>

## 七（末）、Java 工程师在微调项目里的角色

很多 Java 工程师一听"微调"就觉得"那是算法的事，我不懂"。错。你在微调项目里是关键角色，只是**不一定要亲手训**：

```text
Java 工程师在微调项目里的职责：
1. 数据管线：从业务日志/数据库抽取训练样本（你最熟的系统）
2. 接入层：把微调好的模型部署成服务，接进你的 Agent（lesson03 推理优化）
3. 评测集成：把业务评测集接进 CI，自动跑微调前后对比
4. 成本治理：模型路由、预算拦截（lesson04 平台工程）
5. 决策参与：用本节判断力判断是否值得微调

你不用成 PyTorch 专家，但要知道：
- LoRA 是什么、为什么省资源（lesson02）
- 微调好的模型怎么用 OpenAI 兼容接口被 Java 调用（lesson03）
- 怎么用评测量化收益（本节 + 第十六章）
```

<callout emoji="✅"><p>现实分工：算法同学负责"训出好模型"，你负责"把模型变成生产服务、管控成本、量化收益、接进 Agent"。这一节你练的判断力，是连接业务和算法的桥梁——往往比"会跑训练脚本"更稀缺。</p></callout>


## 七（加）、领域适配的三种粒度

微调不是"一锅炖"，按适配粒度分三种，成本和收益天差地别：

```text
粒度            改什么                  成本        适用
──────────────────────────────────────────────────────────────
Token 级        词表/特殊 token 适配     低         领域术语多（医疗/法律生僻词）
Task 级        特定任务行为（LoRA）     中         风格/格式/领域推理（最常见）
Domain 级       整体领域语感             高         全领域重塑（接近预训练，慎做）
```

对 Java 工程师最实用的是 **Task 级 LoRA**：只教模型"在你这个具体任务上怎么表现"，不动它的通用能力，成本低、风险小、可叠加多个 LoRA（一个管格式、一个管话术）。

<callout emoji="💡"><p>进阶玩法：多 LoRA 组合。把"格式 LoRA""话术 LoRA""领域术语 LoRA"分别训，推理时按需叠加——比训一个大而全的模型灵活，也方便单点更新。这是企业落地里很实用的工程技巧。</p></callout>

## 七（QA）、常见误区问答

整理几个我被问得最多的问题，直接答：

```
Q1：微调后模型变"笨"了怎么办？
A：大概率是灾难性遗忘或学习率过大。降学习率、在训练集混入 10%-20% 通用样本、
   减小 LoRA rank。用前面评测双线（新任务+通用）监控。

Q2：我数据只有 200 条，能微调吗？
A：风格/格式类勉强可试（几百条起）；领域推理类 200 条太少了，先 RAG 顶着，
   攒数据。小样本硬上 = 过拟合。

Q3：微调能替代 RAG 吗？
A：不能。知识类永远 RAG 更优（实时、可更新、可溯源）。微调负责"怎么表现"，
   RAG 负责"知道什么"，二者互补。

Q4：基础模型升级，我的 LoRA 还能用吗？
A：通常不能跨大版本直接用，要在新基座上重训/适配。所以 LoRA 要版本化管理，
   绑定 base model 版本，纳入 CI 评测。

Q5：自己训还是用平台（百炼/千帆）？
A：没 GPU 团队 → 用云微调平台（百炼/OpenAI）；有数据隐私要求 → 私有化训；
   绝大多数企业用平台就够了，别重复造轮子。
```

## 七（归）、效果归因：收益到底来自微调还是数据

一个极易混淆的点：你微调后效果好了，但**真的是微调的功劳吗**？很多时候，收益来自"顺便整理了数据/清洗了标注"，而非微调方法本身。归因方法：

```text
归因对照实验（控制变量）：
A 组：原模型 + 整理后的干净 Prompt + RAG   → 测基线提升
B 组：A 组基础上 + LoRA 微调               → 测增量提升
  若 A 组已解决 80% 问题 → 微调只是锦上添花，ROI 低
  若 B 组相对 A 组仍有显著提升 → 微调真有用，值得做

另一个混淆：数据蒸馏
  用强模型生成"理想输出"当训练样本 → 效果提升可能来自"强模型答案质量"
  而非 LoRA 学会了能力。此时要问：直接调用强模型(路由)是否更省？
```

<callout emoji="💡"><p>归因思维是架构师的基本功。很多"微调成功案例"刨掉数据清洗和 Prompt 优化后，微调的边际贡献很小。动手前先做 A/B 归因，避免把功劳算错、把预算投错。这也是为什么 lesson01 反复强调"先试透 Prompt+RAG"。</p></callout>

## 八、企业落地：一个真实决策案例

某银行"智能投顾问答"项目，初期直接上微调（老板拍板"要自研模型"），烧了 2 周 GPU + 标注 3000 条，结果：

```
问题：用户问"某基金最新净值"，微调模型答得头头是道但数据是训练时的旧值
根因：把"实时净值"这种动态知识微调进模型 → 知识过时，还无法溯源
纠正：
  ① 知识类 → 撤下微调，改 RAG 接实时行情库（可更新、可溯源）
  ② 仅保留"投顾话术风格 + 必含免责声明"的微调（这才是微调该干的）
结果：准确率↑、合规风险↓、训练成本降 70%（少训了一大块知识）
```

这个案例完美印证决策框架：**知识给 RAG，风格/强约束给微调，别混**。

## 九、面试自测

1. **解决问题优先级？** —— Prompt → RAG → 工具 → 微调 → 预训练。
2. **三个该微调的信号？** —— RAG 不够（领域推理）、领域强约束、风格/格式固化。
3. **三个不该微调的陷阱？** —— 当数据库、小样本过拟合、忽视基础模型升级债。
4. **最划算的微调场景？** —— 风格/格式固化（高并发省成本、几百条见效）。
5. **微调 + 系统护栏关系？** —— 微调管"大概率不错"，沙箱/护栏管"绝不出格"，两层都要。

## 十、小结

这一节我们建立了"要不要微调"的判断力：

1. **微调用在最后**：优先级 Prompt → RAG → 工具 → 微调，它贵、慢、难维护、易遗忘。
2. **三元对比**：知识用 RAG，能力用工具，风格/强约束用微调，说明用 Prompt。
3. **三个该微调的信号**：① RAG 够了知识但模型不会"按我们的方式用"（领域推理）；② 领域强约束（合规硬边界）；③ 风格/格式固化（最划算，高并发省成本）。
4. **三个陷阱**：当数据库（该用 RAG）、小样本过拟合、忽视基础模型升级债。
5. **决策表 + 真实案例**：知识给 RAG、风格/强约束给微调，别混；动手前用评测量化差异。
