## 一、什么是 Agentic AI

先给定义，再去歧义。

**Agentic AI（智能体人工智能）**：一类以"自主完成目标"为导向的 AI 系统，具备**感知（上下文）→ 推理（规划）→ 行动（工具/环境交互）→ 反思（自我修正）**的闭环能力，且能在不确定性中持续向目标推进，而非单次问答。

区分一下容易混的概念：

```text
           普通 LLM 应用  vs  Agentic AI
 ┌────────────────────┐      ┌────────────────────────┐
 │ 用户输入 → 模型 → 输出 │      │ 目标 → 感知 → 规划 → 行动 │
 │ 一次性，无状态闭环     │      │ → 观察结果 → 反思 → 再行动 │
 │ 不调用工具/不持久     │      │ 循环直到目标达成           │
 └────────────────────┘      └────────────────────────┘
 例：翻译、摘要、问答       例：自动处理客诉、跑完一条研发流水线

 一句话：Agentic = LLM + 目标驱动 + 行动闭环 + 自主迭代
```

<callout emoji="💡"><p>秋天给你一个判断标准：如果去掉"循环/工具/记忆"，系统照样能工作，那它大概率只是"LLM 应用"，不是 Agent。Agent 的魂在"自主向目标推进的闭环"。这决定了你该用多重的工程——详见后面 L1-L5。</p></callout>

## 二、L1–L5 智能体演进模型

业界对 Agent 能力有不同分层，我给你一套清晰、好记、且和企业落地对应的 L1–L5 模型：

```text
 L1  响应式助手 (Reactive Assistant)
      = LLM + 提示词，单次问答，无工具
 L2  工具增强 (Tool-Augmented)
      = L1 + function calling / MCP，能查能算
 L3  推理规划 (Reasoning & Planning)
      = L2 + 计划拆解 + 多步执行 + 反思
 L4  多智能体协作 (Multi-Agent)
      = L3 + 多个专精 Agent 协作/编排
 L5  自主组织 (Autonomous Organization)
      = L4 + 自我目标生成 + 动态组队 + 长期演进
```

### L1：响应式助手

能力：靠提示词完成单轮任务。无工具、无状态。
工程形态：一个 `ChatClient` 调用，零编排。
适用：客服 FAQ、翻译、摘要。

```java
// L1 最小形态：一次调用，无工具
String answer = chatClient.prompt()
        .user("把这段话翻译成英文：" + text)
        .call()
        .content();
```

### L2：工具增强

能力：能调用工具获取/操作外部数据。
工程形态：接 MCP / function calling，单 Agent。
适用：查订单、查天气、生成图片。

```java
// L2：注入工具，模型自行决定调用
chatClient.prompt().user(q).tools(weatherTool).call().content();
```

### L3：推理规划

能力：把目标拆成多步计划，执行中反思修正。
工程形态：ReAct / Plan-and-Execute（第八章讲过的认知架构）。
适用：研究综述、代码生成与自测、复杂客诉处理。

```text
   L3 的闭环（核心特征）
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ Thought │──▶│ Action  │──▶│ Observe │
  └─────────┘    └─────────┘    └────┬────┘
       ▲                              │
       └──────────────────────────────┘
       反思后决定下一步，直到目标达成
```

### L4：多智能体协作

能力：多个专精 Agent 分工协作，由编排者调度。
工程形态：Supervisor / Graph（第四、五章）。
适用：数字员工流水线、研发协作、跨系统业务。

### L5：自主组织

能力：自己生成子目标、动态组建 Agent 团队、跨长期任务自我演进。
工程形态：目前 Mostly 研究/实验中，少数前沿生产试点。
适用：长期自治的运营 Agent、科研助手。

<callout emoji="⚠️"><p>现实提醒：2026 年绝大多数企业落地在 L2–L3，少量头部到 L4。L5 仍是"演示很惊艳、生产很谨慎"的阶段。别听营销号喊"全员 L5"，你做架构选型时要诚实地问：我的业务真的需要 L4 吗？很多时候 L2 加好工程就够。</p></callout>

## 三、每个阶段对应的工程投入

这是架构师最该记住的一张表——**阶段越高，工程复杂度非线性上升**：

| 阶段 | 核心能力 | 工程投入 | 安全/审计要求 |
|------|----------|----------|---------------|
| L1 | 单轮问答 | 极低 | 几乎无 |
| L2 | 工具调用 | 低（接 MCP） | 工具安全（十二章） |
| L3 | 规划+反思 | 中（编排+记忆） | + 决策审计 |
| L4 | 多 Agent | 高（编排框架） | + 多租户/全链路 |
| L5 | 自主组织 | 极高（自治+治理） | + 强监管+人工兜底 |

```text
   工程复杂度曲线（非线性！）
 投入 │
      │                              ● L5
      │                        ● L4
      │                   ● L3
      │              ● L2
      │        ● L1
      └───────────────────────────────► 阶段
   注意：从 L3 到 L4，复杂度跳变最大（协作/状态/一致性）
```

<callout emoji="💡"><p>决策口诀：**用够用的阶段，别盲目冲高**。一个内部"查文档"助手，L2 足矣；一条跨 5 系统的客诉流水线，才值得上 L4。每升一阶，你都要为"更多自主决策"付出更多安全与审计成本——这正好串起第十二章。</p></callout>

---

## 四、为什么"阶段"对企业落地至关重要

举个例子，某政企要做"政策问答"。如果按 L5 思路设计（自主联网、自主生成子目标），会引入不可控的外网访问和不可解释的生成，过不了等保。按 L2 设计（接内网知识库 MCP + 输出护栏），既满足需求又合规。

```text
   同一需求，不同阶段的落地选择
 需求：政策问答机器人
 ┌────────────────────────────────────────────┐
 │ 错误做法：直接上 L4 多 Agent 自治            │
 │   → 不可解释、难审计、过不了监管             │
 │ 正确做法：L2（知识库 MCP）+ 输出护栏(十二章)  │
 │   → 可控、可审计、合规                       │
 └────────────────────────────────────────────┘
```

## 五、招聘里的"Agentic AI 理解"考什么

面试官不会让你背 L1-L5，但会问："你们那个 Agent 到什么阶段了？为什么这么选？"——这考察的就是你对演进模型的真实理解。给你一段参考作答：

```text
【参考回答骨架】
"我们当前落地在 L3（规划+反思），因为业务是复杂的客诉处理，
 需要多步拆解。没上 L4 是因为协作收益有限、且审计成本陡增。
 安全上我们对 L2 工具做了权限隔离、对输出做了护栏，
 并保留全链路审计以满足监管。"
—— 这段话体现的是"阶段意识 + 工程权衡 + 安全闭环"，是架构师视角。
```

<callout emoji="✅"><p>招聘映射：JD 里"深入理解 Agentic AI 演进""能根据业务合理选型 Agent 复杂度"，考的就是这一节。能讲清 L1-L5 并给出"为什么我们停在 L3"的判断，直接区分"会用框架的人"和"会做架构决策的人"。</p></callout>

我给你一个可操作的决策树：

```text
           业务 → 阶段 决策树
 ┌──────────────────────────────────────────────┐
 │ Q1: 需要调用外部数据/系统吗？                  │
 │   否 → L1（纯问答）                           │
 │   是 ↓                                       │
 │ Q2: 需要多步规划/反思修正吗？                  │
 │   否 → L2（工具增强）                         │

 │   否 → L3（单 Agent 规划）                    │

 │   能 → L4（多 Agent）                         │

 │ Q5: 业务真的需要自我目标生成吗？（极少）       │
 │   是 → L5 试点（务必人工兜底）                │
 └──────────────────────────────────────────────┘
```

## 七、常见认知误区

1. **"Agent = 接了工具的 LLM"**：那是 L2，不是完整 Agent（缺自主闭环）。
2. **"阶段越高越好"**：复杂度与风险非线性上升，过度设计是最大浪费。
3. **"L5 已经成熟"**：2026 仍在探索，生产须人工兜底。
4. **"Agent 不需要人"**：L1-L4 都需要 Human-in-the-Loop 在关键节点把关。

<callout emoji="⚠️"><p>秋天再强调一次：Agentic 不是"全自动代替人"，而是"在可控边界内自主推进、关键节点让人拍板"。把人彻底拿掉，在强监管行业是事故温床。</p></callout>

## 八、用代码看清 L2 与 L3 的本质差异

前面是概念，这里用代码把"L2 工具增强"和"L3 推理规划"的差异敲实。L2 是"模型一次性决定调工具"：

```java
// L2：模型自己决定调哪个工具，一次完成
String ans = chatClient.prompt()
    .user("北京今天适合出差吗？查天气再回答")
    .tools(weatherTool)     // 模型内部自主选 + 调
    .call().content();
// 特征是：黑盒、无显式"计划"、出错难干预
```

L3 是"先出计划，再逐步执行，每步可观察可修正"：

```java
// L3：显式规划 + 逐步执行 + 反思（骨架）
String plan = chat.ask("把目标拆成步骤：" + goal);   // ① 规划
for (Step s : parse(plan)) {
    String obs = executeStep(s);                      // ② 执行+观察
    String thought = chat.ask("基于观察反思：" + obs);// ③ 反思
    if (needsRedo(thought)) s = replan(thought);      // ④ 修正
}
return synthesize();                                  // ⑤ 汇总
// 特征是：过程可见、可中断、可人工介入
```

```text
   L2 vs L3 代码形态对比
 ┌──────────────────────────────────────────────────┐
 │ L2: prompt + tools → 一次 call → 答案（黑盒）    │
 │ L3: plan → loop(step/observe/reflect) → 答案（白盒）│
 │ 差异不在"能不能用工具"，而在"过程是否可控"      │
 └──────────────────────────────────────────────────┘
```

<callout emoji="💡"><p>这段对比是面试利器：当被问"你的 Agent 到 L3 了吗"，你能指出"我们有显式规划和反思循环，所以算 L3"，而不是含糊说"挺智能的"。</p></callout>

## 十、L4 编排的代码骨架（呼应第四章）

L4 不是新概念，是"多个 L3 专精 Agent + 编排者"。给你一个 Supervisor 骨架：

```java
// L4：编排 Agent 调度多个专精 Agent（骨架）
class Supervisor {
    Map<String, Agent> specialists = Map.of(
        "contract", new ContractAgent(),   // L3 专精
        "order",    new OrderAgent(),
        "support",  new SupportAgent());

    String solve(String goal) {
        Plan plan = planner.plan(goal);            // 拆解子任务
        StringBuilder sb = new StringBuilder();
        for (SubTask t : plan.tasks()) {
            Agent a = specialists.get(t.owner());
            sb.append(a.run(t));                   // 派给专精 Agent
        }
        return synthesizer.synthesize(sb.toString());
    }
}
```

<callout emoji="⚠️"><p>L4 的坑在"一致性"：多个 Agent 各自维护上下文，结果可能互相矛盾。生产要做"共享黑板（Blackboard）"或"最终合成校验"，否则拼接出来的答案会前后打架。</p></callout>

## 十一、L5 自主组织的现状与风险

L5 是"自己生成子目标、动态组队"。2026 年它多在研究/演示，生产的现实约束：

```text
   L5 现实约束
 ┌──────────────────────────────────────────────────┐
 │ 风险：自我目标可能偏离人类意图（对齐问题）        │
 │ 成本：自主探索 token 消耗巨大                     │
 │ 合规：无人拍板的自主决策在强监管行业不可接受      │
 │ 结论：试点可以，生产必须 Human-in-the-Loop 兜底   │
 └──────────────────────────────────────────────────┘
```

## 小结

这一节我们建立了 Agentic AI 的认知框架：

- **定义**：目标驱动 + 行动闭环 + 自主迭代，区别于普通 LLM 应用；
- **L1–L5**：响应式 → 工具增强 → 推理规划 → 多智能体协作 → 自主组织；
- **工程权衡**：阶段越高复杂度非线性上升，用够用的阶段；
- **落地**：按业务选阶，强监管场景克制使用高阶能力；
- **招聘**：能讲清 L1-L5 并给出选型判断，体现架构师视角。

下一节我们从"LLM 到 Agent 的必然"角度，拆解能力边界与突破——推理、规划、工具这三者是怎么把"聊天模型"逼成"智能体"的。
