# 第六章第1节：记忆的本质——短期记忆与长期记忆在 Agent 中的作用

大家好，我是秋天。

前面五章我们一直在讲"Agent 怎么动起来"——框架、编排、工具、部署。但从这节课开始，我们聊一个更底层、也更容易被忽视的话题：**记忆**。

很多同学以为"记忆"就是"把对话历史塞进上下文"。太浅了。一个没有记忆设计的 Agent，要么每次都像金鱼（转头就忘），要么上下文越塞越满最后"撑爆"或者"腐烂"。这节课我们先把"记忆到底是什么"讲透，建立短期记忆和长期记忆的双层模型，后面六节再逐层落地。

学完这节课你能：

1. 用"记忆双层模型"重新理解 Agent 的状态管理；
2. 区分短期记忆（上下文窗口）和长期记忆（外部存储）的职责边界；
3. 理解"为什么 Agent 必须有记忆"以及"记忆缺失会出什么事故"；
4. 建立"记忆即上下文工程"的认知，为第十五章铺垫。

## 一、先破一个误区：记忆 ≠ 对话历史

我先泼冷水：**把整个对话历史无脑塞进 prompt，是最粗暴、最不可持续的"伪记忆"。** 它有三个致命问题：

```text
伪记忆（全量历史塞上下文）的崩塌：
  1) 长度爆炸：聊 50 轮，token 数超出上下文窗口 → 直接截断
  2) 上下文腐烂：早期重要信息被中间噪音稀释，模型"注意力分散"
  3) 成本爆炸：每轮都把全部历史重发，账单线性增长
```

所以"记忆"在 Agent 里是一个**工程子系统**，不是一句话能糊弄的。它要解决的核心问题是：**在有限、昂贵的上下文窗口里，让 Agent "记得该记得的、忘掉该忘掉的"。**

<callout emoji="💡"><p>一句话定义记忆：记忆是 Agent 在"当前上下文窗口之外"保存、检索、管理信息的能力。窗口内的叫"工作记忆（短期）"，窗口外的叫"知识/经验记忆（长期）"。两者配合，才是完整记忆。</p></callout>

## 二、记忆双层模型：短期 + 长期

我给你一个贯穿第六章的主模型——**记忆双层模型**：

```text
┌──────────────────────────────────────────────────────────────────┐
│                      Agent 记忆双层模型                           │
│                                                                    │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ 短期记忆（Short-term / Working Memory）                     │  │
│  │  载体：当前上下文窗口（prompt 内的 messages）               │  │
│  │  特点：快、贵、容量有限、随会话存在                          │  │
│  │  作用：支撑"当前这轮"推理需要的即时信息                      │  │
│  │  管理：窗口裁剪、摘要、缓存（lesson02）                     │  │
│  └────────────────────────────────────────────────────────────┘  │
│                          │ 写入/检索                               │
│                          ▼                                        │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ 长期记忆（Long-term Memory）                                │  │
│  │  载体：外部存储（向量库 / 关系库 / KV）                     │  │
│  │  特点：慢一点、便宜、容量近乎无限、跨会话持久                │  │
│  │  作用：存"用户画像/历史经验/知识沉淀"，需要时检索回来       │  │
│  │  管理：Embedding/向量检索/遗忘（lesson03-07）               │  │
│  └────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

类比人脑：短期记忆是你"现在脑子里想的"，长期记忆是"你存在硬盘/笔记本里的"。人脑也是先把当前事放短期，重要的事再巩固进长期。

<callout emoji="✅"><p>记忆点：短期记忆解决"这一轮怎么答"，长期记忆解决"它懂不懂这个用户、记不记得以前的事"。两个职责完全不同，别混为一谈。</p></callout>

## 三、短期记忆：为什么必须有，又为什么不够

### 3.1 短期记忆的作用

短期记忆就是"当前这次推理能看到的信息"。它必须包含：

- 系统指令（你是谁、规则）
- 近几轮对话（用户刚说了什么、你刚答了什么）
- 当前工具调用结果与中间状态
- 临时变量（session state）

没有它，Agent 连"用户在问什么"都不知道，更别说多轮对话了。

### 3.2 短期记忆的天花板

但短期记忆受**上下文窗口**硬限制（即使 Gemini 有 100 万 token，也不是无限的，且越长越贵越容易腐烂）。所以短期记忆必须"精打细算"——后面 lesson02 专门讲窗口管理和 LRU/TTL 缓存。

```text
上下文窗口（如 128K / 1M token）是稀缺资源：
  指令 2K + 知识 30K + 历史 40K + 工具结果 20K = 已用 92K
  剩余空间越来越少 → 新信息塞不进 → 必须"丢"或"压"
```

<callout emoji="⚠️"><p>现实提醒：上下文窗口不是"越大越好用"。研究表明，关键信息放在窗口中部时，模型注意力会下降（"Lost in the Middle" 现象）。所以"塞满"不等于"记得住"。这正是第十五章"上下文工程"要解决的——Select/Compress 策略。</p></callout>

---

## 四、长期记忆：让 Agent "越用越懂你"

短期记忆随会话结束或窗口裁剪消失。但真正有价值的 Agent（客服、私人助理、代码助手）需要**跨会话记住用户**。这就是长期记忆。

### 4.1 长期记忆存什么

```text
长期记忆的三类内容：
  1) 用户画像（User Profile）：偏好、习惯、身份、历史诉求
  2) 经验/案例（Episodic）：上次怎么解决的、踩过什么坑
  3) 知识沉淀（Semantic）：业务规则、FAQ、文档片段（常来自 RAG）
```

### 4.2 长期记忆为什么用向量库

长期记忆的检索不是"精确等于"，而是"语义相关"。用户说"上次那个退货的事"，你要找回"三个月前那笔订单的退换货记录"——这是语义匹配，传统 SQL `=` 查不出来，得用向量相似度（lesson03/04 详讲）。

```text
精确查询（SQL）：  WHERE order_id = '12345'        ← 短期/结构化
语义查询（向量）： "上次退货" ≈ 退换货记录向量      ← 长期/非结构化
```

<callout emoji="💡"><p>关键区分：结构化、确定的事实（订单号、用户ID）走数据库精确查；模糊、语义的"记忆"（偏好、经历、经验）走向量库语义查。两类存储配合，才是完整的长期记忆。</p></callout>

## 五、没有记忆设计的真实事故

讲理论太虚，我给你三个"记忆缺失"导致的真实翻车场景，你就知道这章多重要：

```text
事故1：金鱼客服
  用户第一轮："我是VIP，你们承诺优先处理"
  用户第十轮："帮我催一下"
  Agent（无长期记忆）："您好，请问您是什么身份？"
  → 用户怒删App。VIP 身份没被记住。

事故2：上下文腐烂
  前 30 轮聊方案 A，第 31 轮切到方案 B。
  Agent 把方案 A 的约束和 B 混在一起回答
  → 给出自相矛盾的方案，用户懵了。

事故3：重复踩坑
  上周用户问过"发票怎么开"，Agent 答错被纠正。
  这周同样问题，Agent 又答错。
  → 没有经验记忆，错误无法沉淀。
```

这三个事故分别对应：长期记忆缺失、短期记忆管理不当、经验记忆未沉淀。第六章就是教你怎么一个一个填坑。

<callout emoji="⚠️"><p>企业落地铁律：凡是"面向同一个用户反复交互"的 Agent（客服、助理、导师），长期记忆不是可选项，是必选项。没有它，用户体验会从"智能"退化成"每次重新认识你"。</p></callout>

## 六、记忆与上下文工程的关系（提前串接）

我在第十五章会系统讲"上下文工程 Context Engineering"。这里先埋个伏笔：**记忆管理的本质，就是上下文工程的一个子集**。

Context Engineering 四大策略里，至少有三个和记忆直接相关：

```text
Context Engineering 四策略 vs 记忆：
  Write   （写入）  ← 长期记忆的"存"
  Select  （选择）  ← 短期记忆的"挑哪些进窗口"
  Compress（压缩）  ← 短期/长期记忆的"压"
  Isolate （隔离）  ← 多用户/多任务记忆互不污染
```

所以你学第六章，其实也是在为第十五章打地基。记忆是"内容"，上下文工程是"怎么用好这些内容"。

<callout emoji="✅"><p>认知升级：别把"记忆"和"上下文工程"割裂。记忆解决"信息存哪、怎么找"，上下文工程解决"这一轮该把哪些信息放进窗口、怎么放"。两者是同一枚硬币的两面。</p></callout>

## 九、记忆研究溯源：MemGPT 与 Generative Agents

理解记忆不能只停留在工程。学术界早就把"记忆"当核心课题。两个奠基性工作值得你读：

```text
MemGPT (2023, UC Berkeley)：
  提出"分层记忆"——把上下文窗口当"CPU 寄存器"，
  外部存储当"内存/硬盘"，用函数调用在层间搬运信息。
  → 直接启发了 ADK/LangChain 的窗口管理思想。

Generative Agents (2023, Stanford)：
  25 个 AI 智能体在小镇生活，核心机制是
  "记忆流 + 反思 + 规划"。
  → 记忆流记录一切，反思把记忆提炼成高层洞察。
  → 我们的"摘要/提炼"正是对反思的简化。
```

<callout emoji="💡"><p>读论文不是为了掉书袋，而是看"高手怎么抽象问题"。MemGPT 的"窗口=寄存器、外部=内存"隐喻，是理解短期/长期分工最精准的比喻。面试能把这个类比讲出来，比背 API 高级。</p></callout>

## 十、记忆与幻觉：为什么"记错比不记更糟"

一个反直觉事实：**有记忆的 Agent，如果记错了，比没记忆更危险**。因为没记忆时模型会"说不知道"，记错时它会"自信地编造"。

```text
场景对比：
  无记忆 Agent：用户问"我上次的订单号？" → "抱歉我不记得"
              （安全，但体验差）
  记错记忆 Agent：用户问同样问题 → "您的订单号是 X（其实是别的用户的）"
              （危险！泄露+错误）
```

所以记忆系统的第一要务不是"记得多"，而是"记得准 + 知道自己的记忆边界"。这引出"记忆置信度"概念（lesson07 展开）。

<callout emoji="⚠️"><p>设计原则：当记忆不确定时，Agent 应该"明示不确定"而非"硬编"。这在金融/医疗场景是合规底线。"我查到您可能有两笔相关订单，请确认"比"您的订单是 X"安全十倍。</p></callout>

## 十一、短期记忆的心理学启示

人脑短期记忆有"容量限制"（米勒定律：7±2 个组块）。Agent 的上下文窗口同理——不是越长越能装，而是越精越好。

```text
心理学 → 工程映射：
  组块化（Chunking）   → 把多轮对话压缩成"一个事实组块"
  复述（Rehearsal）    → 重要信息反复置顶（常驻卡）
  衰退（Decay）        → 超时信息 TTL 淘汰
  干扰（Interference）  → 噪音信息挤占注意力（上下文腐烂）
```

<callout emoji="✅"><p>用"组块化"思想优化短期记忆：与其塞 10 条零散对话，不如压成 1 条"用户画像组块"。这正是 lesson02 摘要策略的心理学依据。</p></callout>

## 十二、长期记忆的一致性挑战

长期记忆跨会话、跨时间，一致性是难題。

```text
长期记忆一致性问题：
  1) 时序一致性：新记忆不能和已确认的事实矛盾
  2) 来源一致性：多源记忆冲突时选哪个
  3) 演化一致性：用户偏好变了，旧记忆要更新而非并存
  → 这些就是 lesson07 "遗忘与冲突"要解决的
```

## 十三、记忆系统评估四维

怎么判断一个记忆系统好不好？四个维度：

```text
记忆质量四维：
  ① 相关性：召回的记忆是否真相关（查准率）
  ② 时效性：是否优先近期、是否已过期（lesson05/07）
  ③ 一致性：是否存在矛盾记忆（lesson07）
  ④ 成本：检索/存储/压缩的花销（lesson02/05）
```

<callout emoji="💡"><p>评估维度直接对应第十六章"评测闭环"。记忆不是"建好就完事"，要用这四个维度持续评测、持续优化。没有评测的记忆系统，等于盲调。</p></callout>

## 十四、记忆与 RAG 的边界

很多同学分不清"记忆"和"RAG"。一句话厘清：

```text
记忆（Memory）  vs  检索增强（RAG）：
  记忆：Agent 自己产生/积累的信息（用户说过什么、做过什么）
   RAG：从外部知识库检索（文档/手册/网页）

  交叉点：RAG 检索到的知识，也可存入"长期记忆"避免重复检索
  → 记忆是"个性化的、Agent 特有的"；RAG 是"通用的、文档的"
```

<callout emoji="✅"><p>记忆 = "关于这个用户/这次任务的知识"；RAG = "关于世界的通用知识"。两者常被混用，但权属不同：记忆是 Agent 私有积累，RAG 是共享文档。第七章专讲 RAG。</p></callout>

## 十五、企业场景：三类必须记忆的 Agent

```text
必须上记忆的 Agent 类型：
  1) 私人助理类：要记住你的偏好、习惯、历史（强长期记忆）
  2) 客服/顾问类：记住用户身份、工单、过往诉求（长期+短期）
  3) 代码/文档助手类：记住你的代码库上下文、项目约定（长期）
  反例：一次性问答机器人（如"汇率查询"），短期即可，不必长期
```

<callout emoji="⚠️"><p>不是所有 Agent 都需要长期记忆。给"一次性工具型 Agent"强加长期记忆，是过度设计。判断标准：用户会不会"反复回来、且期望你记得他"。会，才上长期记忆。</p></callout>

## 十六、避坑清单

```text
记忆认知避坑：
❌ 把全量对话历史当记忆（爆窗口/腐烂）
❌ 只记不遗忘（漂移/冲突）
❌ 记错还自信（比不记更危险）
❌ 给一次性 Agent 强加长期记忆（过度设计）
❌ 忽略多租户隔离（记忆串号=事故）
✅ 短期管窗口、长期管仓库，分层清晰
✅ 记忆要带置信度与时间戳
✅ 用评测驱动记忆优化
```

<callout emoji="💡"><p>这节课是第六章的"世界观"。后面六节是在这个世界观下，逐一落地：lesson02 短期、lesson03-04 长期存储检索、lesson05 优化、lesson06 最佳实践、lesson07 遗忘冲突。现在你有了地图。</p></callout>

## 十七、动手实现一个最小记忆系统（综合示范）

光讲概念不够，我们用 Java 把"短期 + 长期"两层记忆串成一个最小可运行系统，让你看到全貌。

```java
package com.camp.memory;

import java.time.Duration;
import java.util.List;

/**
 * 最小记忆系统：短期（窗口）+ 长期（向量库，此处用内存 Map 模拟）。
 * 真实长期记忆用 lesson03 的向量库替换 inMemoryLongTerm。
 */
public class MinimalMemorySystem {

    // —— 短期：滑动窗口 ——
    private final SummarizingWindow shortTerm = new SummarizingWindow(6);

    // —— 长期：模拟向量库（真实用 PgVector/Milvus）——
    private final java.util.Map<String, String> longTerm = new java.util.HashMap<>();

    // 常驻用户卡
    private final String userCard;

    public MinimalMemorySystem(String userCard) { this.userCard = userCard; }

    /** 一轮对话：先存短期，关键事实提炼后存长期 */
    public void onTurn(String userMsg, String agentReply) {
        shortTerm.add("U: " + userMsg);
        shortTerm.add("A: " + agentReply);
        // 简化：把"含关键事实"的话存长期（真实用模型提炼）
        if (userMsg.contains("我是") || userMsg.contains("喜欢")) {
            longTerm.put("fact_" + System.nanoTime(), userMsg);
        }
    }

    /** 生成给模型的上下文：短期窗口 + 长期相关回忆（此处全量，真实用检索） */
    public String buildContext(String currentQuery) {
        StringBuilder sb = new StringBuilder();
        sb.append("[用户卡] ").append(userCard).append("\n");
        sb.append("[短期] ").append(shortTerm.snapshot()).append("\n");
        if (!longTerm.isEmpty()) {
            sb.append("[长期回忆] ").append(longTerm.values()).append("\n");
        }
        sb.append("[当前] ").append(currentQuery);
        return sb.toString();
    }

    // SummarizingWindow 见 lesson02，此处为示意引用
    static class SummarizingWindow {
        private final int n; private final java.util.Deque<String> q = new java.util.ArrayDeque<>();
        SummarizingWindow(int n){this.n=n;}
        void add(String s){q.addLast(s);while(q.size()>n)q.pollFirst();}
        List<String> snapshot(){return java.util.List.copyOf(q);}
    }
}
```

<callout emoji="💡"><p>这个 60 行的小系统，已经包含了记忆的全部核心：短期窗口管当下、长期仓库管跨会话、用户卡常驻、关键事实提炼入库。后面 lesson02-07 不过是把每个部件做"工业级加固"。先有全貌，再抠细节，学习才不迷路。</p></callout>

## 十八、记忆与多 Agent 协作

记忆在多 Agent 系统里更复杂：多个 Agent 共享还是各自记忆？

```text
多 Agent 记忆拓扑：
  方案A 共享记忆：所有子 Agent 读同一份长期记忆
        优点：一致性高  缺点：噪音互相干扰
  方案B 各自记忆：每个子 Agent 私有记忆
        优点：专注  缺点：信息不互通
  方案C 共享+隔离：公共记忆（用户画像）+ 私有记忆（专业上下文）
        优点：兼顾  ← 推荐
```

<callout emoji="⚠️"><p>推荐方案 C：公共记忆存"用户是谁、偏好什么"，私有记忆存"这个专家需要的领域上下文"。这和我们第四章多 Agent 协作、第五章子 Agent 状态共享的设计一脉相承——记忆也要分层治理。</p></callout>

## 二十、认知科学视角的记忆（延伸）

Briefly 借认知科学加深理解：

```text
人类记忆三阶段 → Agent 映射：
  编码（Encoding）  → Embedding 把文本变向量
  存储（Storage）   → 写入向量库/数据库
  提取（Retrieval） → 相似度检索召回
  巩固（Consolidation）→ 摘要/提炼，重要记忆强化
  遗忘（Forgetting） → lesson07 衰减/淘汰
```

<callout emoji="💡"><p>Agent 记忆本质上是"用工程手段模拟人类记忆的功能"。理解这个映射，你设计记忆系统时就有了"生物学直觉"——为什么需要巩固（摘要）、为什么需要遗忘（衰减），都不是拍脑袋。</p></callout>

## 二十一、避坑再强化

```text
记忆系统最贵的 5 个错误：
  1) 全量历史塞窗口 → 爆/腐烂
  2) 只记不遗忘 → 漂移/冲突（lesson07）
  3) 无多租户隔离 → 串号事故
  4) 存原文不提炼 → 检索噪音大
  5) 无评测 → 不知道记忆到底有没有用
```

<callout emoji="⚠️"><p>这 5 条对应第六章每一节的"反面教材"。把第六章学完，这 5 条错误你一条都不会犯——这就是课程的价值。</p></callout>

## 二十二、记忆系统的演进路线

把记忆能力按成熟度分成四级，帮你定位自己项目在哪、该往哪走：

```text
L0 无记忆：每次独立对话，无状态
L1 窗口记忆：滑动窗口/摘要，仅当前会话
L2 长期记忆：向量库检索，跨会话个性化
L3 治理记忆：遗忘/冲突/健康度监控（lesson05-07）
L4 自主记忆：Agent 自决"记什么、忘什么"（前沿）
```

<callout emoji="💡"><p>你学完第六章，能力落在 L2~L3。L4 是当前研究热点（如 MemGPT 的自我管理），生产尚早。别焦虑"做不到 L4"——绝大多数企业场景 L2+L3 足够，L4 是学术炫技。</p></callout>

## 二十三、记忆与隐私合规

记忆系统天然存"用户隐私"，合规是红线。

```text
记忆合规要点：
  ✅ 敏感字段脱敏后存（手机号/身份证掩码）
  ✅ 用户有权"遗忘"（删除自己的记忆）
  ✅ 数据驻留合规区域
  ✅ 记忆访问留审计日志
  ❌ 明文存隐私、跨租户共享、无删除通道
```

<callout emoji="⚠️"><p>"被遗忘权"是 GDPR/国内个保法的硬性要求。记忆系统必须提供"删除某用户全部记忆"的通道，否则违规。这是很多团队忽略的合规坑。</p></callout>

## 二十五、记忆系统的故障模式与排查

给你一张记忆系统常见故障表，覆盖 80% 的线上问题：

```text
故障1：Agent 突然"不认得"老用户
  原因：长期记忆隔离失效 / 检索失败 → 查 user_id 过滤与向量库连通
故障2：回答越来越离谱
  原因：记忆漂移，旧错误记忆被反复召回 → 查遗忘机制是否生效
故障3：回答自相矛盾
  原因：知识冲突未裁决 → 查冲突检测
故障4：成本异常高
  原因：每次全量历史塞窗口 / 无缓存 → 查短期记忆管理
故障5：检索召回无关
  原因：Embedding 模型不一致 / 未做重排 → 查 lesson04
```

<callout emoji="⚠️><p>这张表是第六章的"故障字典"。每次记忆出问题，先对照定位是哪一层（短期/长期/检索/遗忘），再对症下药。比盲目改指令高效得多。</p></callout>

## 二十六、记忆驱动的产品价值

把技术拉回业务：记忆到底给产品带来什么？

```text
记忆带来的产品价值：
  1) 连续性体验：用户不用每轮重新自我介绍（留存↑）
  2) 个性化：越用越懂你，推荐/回答更准（转化↑）
  3) 效率：复用历史上下文，少问少查（成本↓、延迟↓）
  4) 信任：记得承诺过的事，用户感觉"被重视"（满意度↑）
```

<callout emoji="💡"><p>写记忆系统别只盯着技术。向老板/产品汇报时，讲"留存、转化、成本、信任"这四个业务指标，比讲"向量相似度"有用。技术人为业务结果负责，这是架构师思维。</p></callout>

## 二十七、记忆与 Agent 自主性的关系

记忆是 Agent "自主"的前提。没有记忆，Agent 每轮都是"失忆的陌生人"，谈不上自主。

```text
自主性层级 vs 记忆：
  L0 无状态：每次重新来，纯响应式
  L1 短期记忆：能续上当前对话
  L2 长期记忆：记得用户，能个性化
  L3 记忆治理：自主决定记什么/忘什么（前沿）
  → 记忆越强，Agent 越"像人"、越自主
```

<callout emoji="💡"><p>这解释了为什么"记忆"是 Agent 架构里如此核心的一章——它不是附属功能，而是自主性的地基。第八章（认知架构）会在此基础上讲规划/反思/学习，而学习的前提就是"记忆能沉淀经验"。</p></callout>

## 二十八、记忆系统的容量规划与成本模型

上生产前算一笔记忆系统的账，避免"上线即破产"。

```text
记忆系统成本构成：
  ├─ 存储成本：向量库存储（按向量条数/维度计费）
  ├─ 写入成本：Embedding 调用（每次写入都算）
  ├─ 检索成本：每次对话的 Embedding + 向量查询
  ├─ 计算成本：压缩/摘要/重排调用的模型
  └─ 运维成本：向量库实例/托管费用

粗算（示意，百万用户）：
  每用户平均 50 条长期记忆 × 1536维 ≈ 存储可观
  日活 10万 × 每轮 1 次检索 Embedding ≈ 日 100万次调用
  → 必须靠 Lesson05 的优化（去重/缓存/分层）压成本
```

<callout emoji="💡"><p>成本意识贯穿全章：记忆不是"存了就完事"，它持续产生存储、检索、计算成本。设计初期就要把"每用户记忆上限、去重、冷热分层"定好，否则规模上来成本失控。这是架构师的预算思维。</p></callout>

## 三十、记忆的本质一句话收束

如果只让你记住一句话，那就这句：

> **记忆的本质，是在"有限且昂贵的上下文窗口"与"无限且廉价的外部存储"之间，做精打细算的调度。**

<callout emoji="✅"><p>这句话是整章的"题眼"。短期记忆管窗口内的精算，长期记忆管窗口外的存储，优化与遗忘管调度的健康。所有技术细节，都是这句话的展开。</p></callout>

## 小结

这节课建立了记忆的整体认知：

1. **破除误区**：记忆 ≠ 全量对话历史，无脑塞上下文会导致长度爆炸、上下文腐烂、成本爆炸。
2. **双层模型**：短期记忆（上下文窗口内，快贵有限）管"这一轮怎么答"；长期记忆（外部存储，慢便宜无限）管"懂不懂这个用户"。
3. **短期天花板**：上下文窗口是稀缺资源，且存在"Lost in the Middle"注意力衰减，塞满≠记得住。
4. **长期必要性**：用户画像、经验、知识三类内容需跨会话持久，且靠向量语义检索而非 SQL 精确匹配。
5. **事故警示**：金鱼客服、上下文腐烂、重复踩坑，三个事故分别指向长期/短期/经验记忆缺失。
6. **与上下文工程关系**：记忆是内容，上下文工程是用法，Write/Select/Compress/Isolate 四策略与记忆一一对应。

记住一句话：**记忆设计的本质，是在"有限且昂贵的上下文窗口"和"无限且廉价的外部存储"之间，做精打细算的调度。**
