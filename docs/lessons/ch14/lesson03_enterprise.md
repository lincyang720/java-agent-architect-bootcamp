## 一、为什么"自研平台"和"写 Agent"是两回事

先划清界限：

```text
   写 N 个 Agent  vs  建 Agent 平台
 ┌────────────────────┐    ┌──────────────────────────┐
 │ 目标：完成具体业务   │    │ 目标：让团队都能低成本造 Agent│
 │ 关注：这个 Agent 对  │    │ 关注：复用、治理、监控、扩缩  │
 │ 关注：工具/记忆/编排 │    │ 关注：平台能力（非业务功能）  │
 │ 产出：业务价值       │    │ 产出：研发效能 + 可控性       │
 └────────────────────┘    └──────────────────────────┘

 一句话：Agent 是"产品"，平台是"生产产品的工厂"。
```

<callout emoji="💡"><p>很多团队卡在"能做几个 demo，但没法规模化"。根因就是没把"平台能力"和"业务 Agent"分开。这一节帮你建立"工厂思维"。</p></callout>

## 二、五大架构考量

### 考量 1：框架选型——统一还是自由？

企业平台常面临"统一框架"还是"各团队自选"的抉择：

```text
   框架选型策略对比
 ┌──────────────────────────────────────────────────┐
 │ 策略 A 强制统一（如全用 Spring AI）                │
 │   + 好治理、好招人、好沉淀公共组件                 │
 │   - 限制创新、特殊场景难满足                       │
 │ 策略 B 自由选型（各取所需）                        │
 │   + 灵活、适配场景                                 │
 │   - 难治理、组件难复用、招人难                     │
 │ 推荐：平台层统一"协议+基础件"，业务层允许差异      │
 │   （MCP 解耦工具，A2A 解耦协作，框架只做壳）        │
 └──────────────────────────────────────────────────┘
```

### 考量 2：技术栈整合——和现有中台打通

Agent 平台不是孤岛，要接企业既有：Spring Cloud、Nacos、Gateway、Sentinel、Seata、ELK、Prometheus。

```text
           Agent 平台与企业中台整合
 ┌──────────────────────────────────────────────────┐
 │ 接入层   Gateway + Sentinel（限流/熔断）           │
 │ 治理层   Nacos（配置/服务发现）+ 权限中心          │
 │ 观测层   OpenTelemetry + ELK + Prometheus/Grafana  │
 │ 数据层   pgvector/Milvus（记忆/RAG）+ MySQL        │
 │ 协议层   MCP Server（工具） + A2A（协作）          │
 │ 业务层   各团队基于平台 SDK 写专属 Agent           │
 └──────────────────────────────────────────────────┘
```

<callout emoji="⚠️"><p>整合的核心原则是"复用而非重建"。企业已有网关/配置中心/监控，Agent 平台就接进去，别另起一套。重复建设是平台项目最常见的死法。</p></callout>

### 考量 3：治理——权限/审计/版本

把第十二章的安全治理"平台化"：

```yaml
# 平台级 Agent 治理配置（示意）
agent-platform:
  governance:
    auth: oauth2 + tenant-isolation      # 多租户隔离
    audit: append-only + otel-trace      # 全链路审计
    rate-limit: sentinel-rules           # 限流
    prompt-versioning: git-backed        # Prompt as Code
    tool-approval: manual-review-for-high-risk
```

### 考量 4：成本治理

第十章讲过，平台层要把成本当一等公民：

```text
   平台成本治理三板斧
 ┌──────────────────────────────────────────────────┐
 │ 1. 模型路由：简单任务走小模型，复杂走大模型        │
 │ 2. 缓存：相同/相似 prompt 命中缓存，省 token      │
 │ 3. 预算：每租户/每 Agent 设 token 预算 + 告警      │
 └──────────────────────────────────────────────────┘
```

### 考量 5：演进——留好扩展点

平台要能跟着框架/协议演进。关键：**所有框架相关代码收敛在适配层，业务不直连框架**。

```java
// 平台适配层：业务只依赖平台抽象，不依赖具体框架
public interface AgentRuntime {
    String run(AgentTask task); // 业务调用，底层可换 LangChain4j/Spring AI/ADK
}
// 平台内部用工厂决定用哪个框架实现，业务无感知
```

<callout emoji="✅"><p>这招叫"依赖倒置"——业务依赖抽象（AgentRuntime），框架是实现细节。哪天 LangChain4j 不流行了，你只改适配层，业务代码不动。这是平台能"长期维护"的命门。</p></callout>

## 三、长期维护：提前埋好的三个坑

1. **Prompt 版本失控**：必须 Prompt-as-Code（Git 管理），否则没人敢改 prompt；
2. **工具 Server 腐化**：MCP Server 越来越多却无目录、无Owner，最后谁都不敢动。要建"工具注册中心 + Owner 制"；
3. **评测缺失**：没有回归评测（第十六章），每次模型升级都靠手测，迟早出事。

```text
   平台长期健康的三个支柱
 ┌──────────────────────────────────────────────────┐
 │ 可观测（OTel+ELK） → 出问题能定位                 │
 │ 可评测（RAGAS+EvalScope）→ 升级有底气             │
 │ 可治理（权限/版本/目录）→ 规模化管理              │
 └──────────────────────────────────────────────────┘
```

## 五、三条学习路径

根据你目标不同，给三条路径：

### 路径 A：转岗 Agent 开发（3-6 个月）

```text
 重点：PART1 基础 + PART2 核心 + 工程化基础
 动作：
 1. 跑通 LangChain4j + Spring AI 每个示例
 2. 手写一个带记忆+RAG 的单 Agent
 3. 加 MCP 工具 + 输出护栏（十二章）
 4. 准备 3 个可演示项目写进简历
```

### 路径 B：进阶 Agent 架构师（6-12 个月）

```text
 重点：+ MCP/A2A + 安全治理 + 上下文工程 + 评测 + 平台
 动作：
 1. 设计一个多 Agent 编排（第四章/十一章 A2A）
 2. 搭一套含审计/多租户的平台骨架（十二章）
 3. 落地上下文工程四大策略（十五章）
 4. 建评测闭环（十六章），能说清选型权衡
```

### 路径 C：面试冲刺（2-4 周）

```text
 重点：能讲清"为什么"而非"怎么写"
 动作：
 1. 背熟 L1-L5、通用vs专用、MCP vs A2A 三张图
 2. 准备"安全三闸门""上下文工程""平台五考量"话术
 3. 每个框架能说出定位差异与选型理由
 4. 项目描述用"MCP+A2A+互操作+审计"关键词（见各章）
```

<callout emoji="⚠️"><p>别贪多。路径 C 的同学千万别去啃微调（十八章）——面试里那是加分项不是门槛，把主线和架构讲透比多学一个冷门技能有用。</p></callout>
