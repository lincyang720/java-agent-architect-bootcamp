## 一、三种控制拓扑：一句话定义

```
┌──────── 中心化 (Centralized) ────────┐
│  一个主控(Supervisor) 协调所有子Agent  │
│  子Agent 不直接互联                    │
│  代表：Supervisor / Sequential / Loop  │
└───────────────────────────────────────┘

┌──────── 去中心化 (Decentralized) ────┐
│  Agent 之间对等、直接通信、自组织协商    │
│  无主控节点                            │
│  代表：消息总线协商(msghub 自由对话)    │
└───────────────────────────────────────┘

┌──────── 层次化 (Hierarchical) ──────┐
│  多层控制：上层主管编排下层团队         │
│  下层内部可再用中心化/去中心化          │
│  代表：Graph 子图 / Supervisor 内含 Loop│
└───────────────────────────────────────┘
```

对应前面章节的落点：
- **中心化**：lesson03 Supervisor、lesson04 Sequential/Loop（一条线/一个主管说了算）。
- **去中心化**：lesson06 的 msghub 自由对话（Agent 间自主协商）。
- **层次化**：lesson02 的子图（subgraph）、Supervisor 内部再跑 ReAct Loop、PlanNotebook 管理多 subtask。

---

## 二、中心化（Centralized）：可控但怕单点

**结构**：星型，主管居中。子 Agent 只跟主管对话。

**优势**：
- 全局视野清晰，流程可预测、易审计（金融/政企最爱）。
- 单点可观测，出问题好定位。
- 子 Agent 职责单一，提示词干净。

**劣势**：
- **单点故障**：主管挂了，全网停摆（lesson03 讲过，需降级/监控兜底）。
- **瓶颈**：所有决策过主管，高并发下主管成吞吐瓶颈。
- **扩展性差**：子 Agent 多了，主管路由逻辑膨胀。

**适用场景**：流程固定、需统一审计、子 Agent 数量可控——客服总机、贷款初审、对账流水线。

---

## 三、去中心化（Decentralized）：灵活但难控

**结构**：Agent 对等，直接通信、自主协商谁接活。

**优势**：
- 无单点，某 Agent 挂了其他能补位，鲁棒性强。
- 天然支持并行、动态扩缩。
- 适合开放式、涌现性任务。

**劣势**：
- **不可预测**：谁干了啥、为什么这么干，难追踪（黑盒）。
- **难调试**：出了问题定位不到责任节点。
- **易活锁**：Agent 互相等待/互相推诿（lesson01 讲的活锁）。
- **难审计**：不满足强监管场景。

**适用场景**：探索性研究、开放式创意生成、对可控性要求不高的内部工具——**金融/政企核心链路慎用**。

<callout emoji="⚠️"><p>现实教训：很多团队一开始觉得"去中心化很酷"，结果上线后出了 bug 查三天查不到哪个 Agent 疯了，最后又改回中心化 + 局部并行。去中心化的"灵活性红利"往往抵不过"可控性成本"。除非场景天然适合，否则默认中心化。</p></callout>

---

## 四、层次化（Hierarchical）：兼顾可控与规模

**结构**：多层控制。上层主管编排"下层团队"，下层内部再用中心化或去中心化。

```
        ┌── 总控 Supervisor ──┐
        │  (拆任务、定策略)     │
        └──┬─────────┬────────┘
           ▼         ▼
      ┌─团队A─┐  ┌─团队B─┐
      │主管+子 │  │主管+子 │   ← 下层各自是中心化小队
      │Agent  │  │Agent  │
      └───────┘  └───────┘
```

**优势**：
- 兼顾"全局可控"和"局部灵活"：总控保证审计/一致，小队内部可并行/自主。
- 扩展性好：加团队不影响其他团队。
- 故障隔离：某小队出问题不影响全局。

**劣势**：
- 设计复杂，层级划分需要架构功力。
- 跨层通信有延迟和协调成本。

**适用场景**：大型复杂系统——企业级 Agent 平台、数字员工中台、跨域协作（如"营销Agent团队 + 风控Agent团队 + 客服Agent团队"由总控协调）。

<callout emoji="✅"><p>工程经验：层次化是"生产级多 Agent 系统的默认答案"。一个总控 Supervisor 管大流程（可控、可审计），下面每个领域用一个中心化小队或单个 ReAct/Loop Agent（灵活、并行）。这把三种拓扑的优点捏到一起，是 lesson03/04/06/08 各模式的自然组合。</p></callout>

## 五、决策框架：拿到需求怎么选

给你一张可操作的选型表：

| 你的业务特征 | 推荐拓扑 | 代表模式 |
|-------------|---------|---------|
| 流程固定、需审计、子 Agent < 10 | 中心化 | Supervisor / Sequential / Loop |
| 高风险动作多、要人工拍板 | 中心化 + HITL | Supervisor + lesson05 人工节点 |
| 开放式探索、不在意可解释 | 去中心化 | msghub 自由协商 |
| 大型系统、多领域团队、需扩展 | 层次化 | 总控 + 子图/小队 |
| 复杂任务要稳定可控 | 中心化 + PlanNotebook | Supervisor + lesson08 规划 |

一句话口诀：**默认中心化；要规模用层次化；纯探索才去中心化；高风险必加 HITL；复杂任务必加 PlanNotebook。**

## 七、企业场景：一个数字员工中台的拓扑选型

某银行"数字员工中台"最终落地架构（层次化 + 中心化 + HITL）：

```
总控 Supervisor（层次化顶层）
  ├─ 客服团队（中心化小队：路由+专线Agent）
  ├─ 风控团队（中心化小队：征信+规则+模型）
  └─ 审批团队（中心化 + HITL：人工终审节点）
        │
        └─ 每个复杂子任务内部用 ReAct+PlanNotebook（lesson06/08）
           全部跑在沙箱+审计（lesson07）之上
```

它完美体现了本章所有模式的组合：层次化管全局、中心化管团队、HITL 管高风险、PlanNotebook 管复杂任务、沙箱审计管安全。这不是"炫技"，而是每一个选择都对应一个真实风险点的兜底。

## 九、中心化落地清单

当你判断"用中心化"，照着这张清单落地：

```
✅ 一个明确的 Supervisor（或 Sequential/Loop 线性流）
✅ 子 Agent 职责单一、提示词精简
✅ Supervisor 路由失败有默认降级（lesson03）
✅ 高风险动作接 HITL（lesson05）
✅ 全链路可观测 + 审计（lesson07）
✅ 单点加限流熔断（Sentinel）
```

适用：客服总机、贷款初审、对账流水线、告警处置——流程固定、需审计、子 Agent 可控。

## 十、去中心化落地清单

去中心化慎选，落地清单：

```
✅ 仅在开放式/探索性任务使用
✅ 用消息总线（msghub）而非共享可变状态，降低耦合
✅ 设"空闲超时"防止 Agent 互相空转/活锁
✅ 关键动作仍要 HITL + 审计（不能因去中心化放弃安全）
✅ 不接受强监管场景（金融核心链路）
```

适用：创意生成、研究探索、内部头脑风暴工具。

<callout emoji="⚠️"><p>现实经验：很多团队一开始"去中心化很酷"，上线后 bug 查三天查不到哪个 Agent 疯了，最后改回中心化 + 局部并行。去中心化的"灵活性红利"常抵不过"可控性成本"。除非场景天然适合，否则默认中心化。</p></callout>

## 十一、层次化落地清单

层次化是生产级默认答案，清单：

```
✅ 顶层总控 Supervisor 拆任务、定策略（可控、可审计）
✅ 下层每个领域一个中心化小队或单个 ReAct/Loop Agent（灵活、并行）
✅ 跨层通信有清晰接口，避免层间状态混乱
✅ 故障隔离：小队出问题不影响全局
✅ 复杂子任务内部用 PlanNotebook（lesson08）
```

适用：大型系统、多领域团队、企业级 Agent 平台、数字员工中台。

## 十二、真实故障案例：去中心化的坑

某团队做"智能运维"用纯去中心化，几个 Agent 通过消息总线自由协商处置告警。一次故障：网络 Agent 说"我来处理"，数据库 Agent 也说"我来处理"，两者同时执行了冲突的扩容操作，把集群搞宕机。根因：无主控协调、无锁、无"谁负责"的定义。事后改成"总控 Supervisor 指派唯一负责人 + 其他旁观"，再没出过。

这案例印证 lesson09 的核心结论：**可控性优先于灵活性**。生产系统，默认把决策权收口到中心/层次结构。

## 十六、实战选型工作坊：三个场景现场判断

光讲理论不够，来三个真实需求，现场选拓扑并说理由：

**场景 A：银行"对公贷款初审"**——流程固定（征信→风控→合规→终审），需统一审计，子 Agent 数 < 8。
→ **中心化（Supervisor + HITL）**。理由：强审计、流程固定、高风险动作要人工终审。决不用去中心化。

**场景 B：某内容团队"营销文案头脑风暴"**——要多个视角碰撞创意，不在意可解释，错了没成本。
→ **去中心化（msghub 自由协商）**。理由：探索性、低风险、要多样性。但关键产出仍要人审。

**场景 C：电商"智能客服中台"**——多领域（售前/售后/物流/财务），每领域一个团队，需扩展到几十个 Agent。
→ **层次化（总控 + 领域小队）**。理由：规模大、需扩展、故障隔离、总控保证审计。

记住口诀反复用：**默认中心化；规模用层次化；纯探索才去中心化；高风险必加 HITL；复杂任务必加 PlanNotebook。**

## 十七、多 Agent 的成本与延迟账

选型还要算账。多 Agent 不是免费午餐：

| 维度 | 中心化 | 去中心化 | 层次化 |
|------|--------|---------|--------|
| 单次延迟 | 低（线性） | 中（协商） | 中高（多层） |
| Token 成本 | 中 | 高（重复沟通） | 高（多层 prompt） |
| 运维成本 | 低 | 高（难调试） | 中 |

经验：
- **并行能降延迟但涨 token**：Supervisor 扇出并行，延迟降 N 倍，但每个子 Agent 都带系统提示词，token 翻倍。
- **层级越深，prompt 越胖**：每加一层总控，所有下游都多收一份"总控指令"，成本线性涨。
- **ReAct 最费 token**：自主循环每次迭代都重发历史，长任务 token 爆炸——所以 `maxIters` 也是省钱阀。

<callout emoji="⚠️"><p>成本红线：一个"智能客服"若每次对话都拉 5 个子 Agent 并行、每个带 2000 字系统提示，单次对话成本可能是单 Agent 的 5~8 倍。上线前必须做成本压测（第十章成本治理）。很多 PoC 效果好、一上线账单爆炸，就是没算这笔账。</p></callout>

## 二十、拓扑混合实战：一个系统用三种拓扑

真实企业系统很少"纯中心化"或"纯去中心化"，而是混合。以"智能营销中台"为例：

```
总控 Supervisor（层次化顶层）
  ├─ 策略团队（中心化小队：路由+文案+设计 Agent）
  ├─ 数据团队（中心化小队：画像+归因 Agent）
  └─ 创意探索（去中心化：多个创意 Agent 在 msghub 自由碰撞）
        │
        └─ 关键动作（发券/外发）全部走 HITL 人工确认
```

这里：
- **层次化**：总控 + 小队。
- **中心化**：每个小队内部。
- **去中心化**：创意探索环节（低风险、需多样性）。
- **HITL**：高风险外发动作。

一张图里四种机制各司其职——这才是一线落地的真实形态，而非教科书里的"非此即彼"。

<callout emoji="✅"><p>认知升级：别被"选一种拓扑"的思维限制。架构师的工作是"在系统的不同部位用不同的拓扑"，让每个部位都拿到最适合的控制结构。这是 lesson09 的终极心法。</p></callout>

## 二十一、多 Agent 的运维：版本、灰度、回滚

多 Agent 系统上线后，运维是另一门学问：

- **Agent 版本化**：每个子 Agent 的提示词/模型版本要可追踪，出问题能回滚到上一版。
- **灰度发布**：新 Agent 先接 5% 流量，对比效果（第十六章评测）再全量。
- **流量调度**：Supervisor 可按版本路由（部分用户走新 Agent）。
- **统一观测**：所有 Agent 的 trace/metrics 汇入统一面板（lesson07 企业级）。

```yaml
# 概念：Agent 灰度配置
agents:
  finance_agent:
    stable: version-3
    canary: version-4   # 新版本
    canary_traffic: 0.05
```

## 二十二、与上下文工程的关系（衔接第十五章）

多 Agent 系统的"状态/记忆"本质就是上下文工程（第十五章）的议题。每个 Agent 的私有状态、共享黑板、PlanNotebook 进度，都是"上下文"的不同形态：

- **Write**：Agent 把中间结果写入状态（节点 `return Map`）。
- **Select**：下一节点只读取需要的 key，不污染上下文。
- **Compress**：长状态做摘要/截断，防上下文腐烂。
- **Isolate**：私有状态与共享状态隔离，防互相干扰。

理解这一点，"多 Agent 状态管理"和"上下文工程"就打通了——它们是同一件事的两种视角。

## 二十五、拓扑选择的成本账再算

lesson09 提过成本，这里给一个更落地的"决策公式"：

```
若 子Agent数 ≤ 5 且 流程固定  → 用 Sequential/Loop（省去路由开销）
若 子Agent数 > 5 或 需动态分发 → 用 Supervisor（路由开销值得）
若 跨多领域/需扩展            → 用层次化（隔离故障、独立迭代）
若 纯探索/无合规约束         → 可去中心化（但加审计）
```

关键洞察：**Supervisor 的路由开销（一次额外模型调用 + 更胖的上下文）在子 Agent 少时不划算**。所以"简单任务上 Supervisor"反而更贵更慢。先用顺序/循环，规模上来再升级。

<callout emoji="⚠️️<p>反模式：所有任务都套 Supervisor，觉得"高级"。结果是每个简单问答都多一次路由调用、多一份全领域提示词，延迟和成本白白涨。架构师的价值是"克制"——用最简单能解决问题的模式。</p></callout>

## 二十六、多 Agent 的可观测性串联

多 Agent 系统可观测，要在"编排层 + Agent 层 + 工具层"三层都埋点（对应 lesson07 企业级）：

```
编排层：哪个节点执行、耗时、走向哪条边（Graph trace）
Agent 层：每步 Thought/Action/Observation（ReAct 日志）
工具层：每次 tool_call 入参/出参/延迟/异常
```

三层 trace 用同一个 `threadId` / `traceId` 串联，出问题能从上（编排卡哪）查到下（工具调了啥）。这是多 Agent 排障的"全景视图"。

## 二十九、中心化模式的典型故障与修复

中心化最怕"主管节点逻辑膨胀"。一个真实案例：某 Supervisor 的 router 提示词越改越长，塞了 12 个领域的分类规则，结果模型经常"分错类"或"输出格式乱"。

修复：
1. **拆 router**：用规则/轻量分类器替代 LLM 路由（lesson03 提过）。
2. **领域收敛**：12 个领域合并成 4 个主领域，子 Agent 内部再细分。
3. **输出强约束**：router 只输出枚举值，下游 switch 解析，不依赖模型自由文本。

修复后路由准确率从 82% 提到 99%，延迟还降了（不用每次调 LLM 路由）。这印证"中心化要轻，别把复杂度堆在主管上"。

<callout emoji="⚠️️<p>反模式：把 Supervisor 当"万能分发器"，什么逻辑都往 router 提示词里塞。主管越胖越易错越慢。主管只做"轻量分类 + 分发"，重逻辑下放子 Agent。</p></callout>

## 三十、层次化的团队边界设计

层次化里"总控 vs 小队"的边界怎么划？经验法则：

- **总控负责**：任务拆解、领域分发、跨团队协调、最终汇总、全局策略。
- **小队负责**：本领域内的具体执行、领域内子步骤、领域知识。
- **边界信号**：若两团队频繁互相调用对方内部，说明边界划错，应合并或重划。

边界划错会导致"跨层混乱"——总控绕过直接调小队的子 Agent，或小队擅自做跨领域决策。清晰的边界是层次化可控的前提。

## 三十一、面试终极模拟

模拟一道高频题："设计一个电商智能客服多 Agent 系统。"

标准回答框架：
1. **拓扑**：层次化（总控 Supervisor + 售前/售后/物流/财务小队）。
2. **分发**：Supervisor 按意图路由；高风险（退款/补偿）走 HITL。
3. **协作**：小队内部 Sequential（查知识→生成→自审）。
4. **安全**：工具最小权限 + 沙箱 + 审计（lesson07）。
5. **规划**：复杂任务用 PlanNotebook（lesson08）。
6. **可观测**：全链路 trace + token 成本监控（lesson07 ch03）。
7. **兜底**：路由失败降级默认 Agent + 限流熔断。

按这个框架答，覆盖本章 90% 考点。

## 三十二、小结

这一节我们把第四章收成一张选型地图：

1. 三种拓扑：**中心化**（主管协调，可控但怕单点）、**去中心化**（对等协商，灵活但难控）、**层次化**（多层控制，兼顾可控与规模）。
2. 模式归类：Supervisor/Sequential/Loop=中心化；msghub 自由对话=去中心化；Graph 子图/Supervisor 内含 Loop=层次化。
3. 中心化优势在可控可审计，劣势在单点/瓶颈；去中心化相反；层次化取两者之长但设计复杂。
4. 决策框架：默认中心化，规模用层次化，纯探索才去中心化；高风险必加 HITL，复杂任务必加 PlanNotebook。
5. 生产落地：数字员工中台 = 层次化顶层 + 中心化团队 + HITL + PlanNotebook + 沙箱审计，是各模式的有机组合。
6. 架构师思维：不是"会用某个模式"，而是"知道什么时候不用它"——按业务特征选型。

**第四章到此结束。** 你现在已经具备设计多 Agent 系统的完整能力：从通用模型（lesson01）、编排引擎（lesson02）、各控制模式（lesson03~04）、安全与介入（lesson05/07）、自主规划（lesson06/08），到选型决策（lesson09）。下一章我们进入 **Google ADK for Java**，看另一个主流框架如何做 Agent 创建与编排，拓宽你的框架视野。
